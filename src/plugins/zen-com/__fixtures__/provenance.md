# ZEN.COM source evidence

## Current implementation and scope

The plugin uses only `https://api.zen.com/mobile/` for bank authentication, accounts and history. Standalone portal login, portal cookie restoration/refresh, cloning-token acquisition and web-session cloning were removed on 2026-10-20 at the owner's request. `useMobileAuth` is no longer a setting; old stored values cannot enable the removed path. The owner-controlled iDenfy browser UI remains part of mobile identity verification, not portal authentication.

MobileAuth version 1 remains compatible with the previously tested native connection: deviceId, loginToken and verified app passcode. Successful cold or fast login immediately saves the final rotated token before any financial request. Financial requests use that invocation's Access-Token and the same connection device identity. Unknown authentication, transport, bank and schema failures remain ordinary reportable errors and stop the whole synchronization; they never trigger an unconfirmed SMS fallback or return partial financial data.

The app passcode uses numberPassword and its prompt explains connection-scoped storage. Background cold login stops before phone/SMS interaction. After successful face verification in the external browser the owner returns to Zenmoney and closes the launcher; the workflow then requires bank-confirmed SUCCESS before identity/verify. A rejected current face attempt stops immediately even when the outer verification remains ACTIVE. Scheduled background execution and a month without synchronization remain unverified.

## Official application and protocol evidence

The official Huawei AppGallery distribution was linked by ZEN's [download page](https://www.zen.com/pl/appdownload/): store ID C103718927, package com.zen.application, version 2.14.3. APK downloaded on 2026-10-17 from `https://appgallery.cloud.huawei.com/appdl/C103718927`; SHA-256 `1004118773b88a8874372541d5a81f4bfd6103a5e9e8e1788892a682f9941588`. APKs, decompiled sources and raw captures remain ignored local research artifacts. JADX 1.5.6 reported reconstruction errors, including 108 errors processing classes6.dex; API annotations/serialization evidence below was independently checked against successful owner-authorized requests.

- d60.b and the auth serializers establish initial authentication, OTP/passcode verification, authentications/fast-login and token replacement. Device metadata comes from si0.a / DefaultHeadersInterceptor. Device-Id and Installation-Id are a persisted connection UUID. The native Android ID is unavailable to plugins; the same connection UUID is used as Mobile-Device-Id, accepted in observed owner-controlled cold and repeated fast-login runs. No other device's trusted identifier is copied.
- The official mobile-services and fingerprint providers allow unavailable native services. The implemented extended fingerprint is `ZEN;` plus Base64 UTF-8 JSON with version 1.0 and SEON/THREATMETRIX entries carrying empty values. This exact fallback was accepted in the observed owner-controlled flows; it does not establish acceptance for all accounts/devices.
- t30.a: GET v2/accounts with hidden, balanceCurrency and checkCache. RemoteAccountsRepository's update coroutine requests hidden=true and handles hidden accounts locally. The verified request uses `v2/accounts?hidden=true&checkCache=false`, omitting nullable balanceCurrency, and returns all 35 balances including 31 hidden currencies. There is no account pagination envelope in this observed API; the complete accounts array is the account graph.
- po1.b: GET history-entries; oo1.c builds optional lastHistoryEntryId and filter queries without a page-size parameter. The verified unfiltered endpoint returns 20 entries per full page. Requests continue using the last returned history-entry ID until the explicit isLastPage flag; an empty nonterminal page or repeated cursor fails visibly. No ordering assumption or short-page heuristic replaces that flag.
- The bank's response dates include UTC offsets. Filtering uses transaction.createdAt and inclusive fromDate/toDate; a nullish upper bound is unbounded. No date-only server filter is added or guessed. A repeated invocation still traverses the bank cursor history before local interval filtering.
- TransactionResponse and owner/party serializers show the common financial fields plus settlementEur, terminal.mcc, additionalInfo, merchantDetails and virtual-account metadata. Numeric original/settlement/fee amounts are strings in the observed mobile response, rather than the earlier portal's JSON numbers. All actual values were checked for numerical equality, not coerced into invented amounts.

## Complete mobile financial comparison

Owner-triggered native session c03233c0-2776-47f4-8b58-609c67747af1 on 2026-10-20 supplied a fresh implemented fast-login. The investigation made read-only account/history requests with that current Access-Token and did not replay unmanaged login requests or rotate saved state. It collected one complete account response and 36 complete history pages, 708 records, reaching isLastPage=true. All history IDs match the earlier separately retained complete portal capture. Status counts: 618 HTS_ACCEPTED, 90 HTS_REJECTED. Supported observed classes: 385 purchases, 224 exchanges, 39 fees, 22 incoming buddy transfers, 14 top-ups, 11 withdrawals, 8 outgoing transfers, 3 fee corrections and 2 MoneySend credits (including rejected instructions).

Complete reproduction with the mobile converter returns 35 accounts and 618 transactions. Account bank IDs, currencies, titles and balances match the verified prior 35-account result. All 618 complete transactions equal the prior successful native full-history output after applying the shared adapter's external sync-ID trimming and removing only the newly available MCC for that comparison. There are 398 source records with terminal MCC, and 331 converted accepted transactions retain it. No amount, date, fee, movement-ID, counterparty, comment or transfer-side difference was found in that comparison.

Mobile accountNumber is a unique valid primary IBAN per currency in this account graph. The older portal graph supplied only two shared numbers and therefore required a bank-UUID matching fallback. The mobile graph instead uses the primary natural identifier; bank account.id and every movement.id remain unchanged. The complete native graph includes 28 international virtual account numbers and one local virtual account; seven currencies have no international virtual account. Primary and virtual numbers are retained as converter matching context independently of exported minimal syncIds, so known account membership is not lost when detecting a possible internal counterpart. During the first mobile-only owner run, the owner manually linked the returned accounts to the previously imported accounts. Automatic migration matching is not established; the owner subsequently confirmed a repeated synchronization without another login or duplicate accounts/transactions. This repeat is owner-reported; its separate runtime log was not available in the inspected local capture directory.

The owner confirmed financial reconciliation of the earlier complete import on 2026-10-19. Source dates, amounts, and identifiers were compared privately; no bank data was reconstructed from application output as a substitute for source responses.

## Public fixtures and sanitization

- mobile-accounts.json: complete 35-account native response, including all virtual-account, country/routing, hidden, total-balance and other metadata. accounts.ts exposes it as unknown. expected-accounts.ts independently lists the complete expected graph and known-number matching context.
- mobile-history-page1.json, mobile-history-page2.json and mobile-history-terminal.json: complete native pages 1, 2 and 36. Intermediate pages remain private; model pagination tests explicitly omit them and do not claim to reproduce the full live traversal.
- mobile-expected-transactions.json: complete first-page domain expectations independently derived from the previously reconciled native full-history output and corresponding source MCC. The expectation restores source full masked-card matching values before the host adapter's trimming and sorts equal-time results by the unchanged movement-ID ordering contract.
- history.ts: the two complete earlier portal limit=10 pages (20 entries); additionalHistory.ts: 17 complete additional incoming buddy, MoneySend, withdrawal and correction records; terminalHistory.ts: complete eight-record final portal page. They remain independent historical financial regression evidence for fields common to both APIs, not live portal dependencies. All source IDs and card/account relationships use consistent public-safe replacements.
- transactionTypes.ts and transactionStates.ts: complete observed dictionary responses. They establish labels but do not manufacture examples of unsupported financial classes.
- mobile-fast-login.json: complete successful fast-login response from c03233c0, replacing token secrets, authentication/customer UUIDs, user login and external reference with format-preserving nonfunctional values. It verifies the mobile-only wire sequence with captured accounts/history. Request credentials and omitted-page sequencing in that test are explicitly modeled.
- mobile-validation-error.json and mobile-device-validation-error.json: complete observed 400 validation responses from the initial empty-identification and empty-Mobile-Device-Id investigations. They contain no real user credentials. Authentication diagnostics retain validation field names and technical messages, masking known echoed credentials/personal values, including in Spring validation messages.
- mobile-otp-response.json, mobile-passcode-response.json and mobile-identity-response.json: complete observed 201/OTP, 200/PASSCODE and 200/IDENTITY steps. A future blockadeExpirationTime on OTP is a resend/submission timer, not proof of a blocked login. Unknown non-OTP timers remain reportable.
- mobile-identity-initialization-response.json: the observed initialized verification session with its own token and verificationId; it is not a normal next-factor response. mobile-identity-requirements-response.json and mobile-face-attempt-response.json preserve the observed FACE_REAUTH / IVP_IDENFY negotiation. mobile-face-rejected-response.json preserves outer ACTIVE with current attempt FAILED, without guessing a biometric rejection reason.

Fixture replacements consistently cover owner/party names, residential addresses, primary and virtual IBANs, masked cards, UUIDs and auth/provider tokens while retaining field presence, empty/null values, complete records, dates, monetary values, currency relationships and identifier collisions. Newly collected native records retain actual empty addresses rather than populating them from unrelated fields. Merchant names, business addresses, MCCs and other public merchant enrichment are intentionally preserved. Reusable credentials never appear in public files; synthetic workflow secrets and fixture tokens are explicitly nonfunctional.

Actual network/navigation logging tests cover request/response credentials, cookies, phone and personal names/addresses, while retaining account/history structure, operation IDs, amounts, merchant information and MCC. Connection-generated device/installation UUIDs and the constant empty-SDK fingerprint are diagnostic metadata, not credentials. Identity providers, methods and statuses remain verbatim, including previously unknown values. Authentication response structure, attempt IDs, token expiry metadata and validation details remain visible under field-level masks; unknown providers still fail visibly. Separate model tests cover new diagnostic labels and secret echoes without claiming support for an unseen bank provider. Raw captures, private replacement maps, source comparisons, APKs, recovery configuration, generated bundles and development plans stay ignored. The repeatable local audit compares known private values against every candidate file and separately scans fixture UUIDs/JWTs/full-PAN patterns; it is bounded source comparison, not a universal PII classifier.

## Financial interpretation and remaining gaps

Top-up fee metadata is informational when the actual fee is a separate entry sharing timestamp, owned account, amount, currency and status: import the separate fee once. Unknown nonzero fee representation fails instead of inventing a split. Accepted exchanges explicitly provide two owned account movements and their currencies. MoneySend identifies the receiving ZEN card, so it must not assign that card to the unknown external source. Withdrawals preserve the original-currency cash side and settlement-currency bank debit. ATM fee corrections are separate booked expenses with their supplied purpose. Purchase/card titles matching the source card's last four digits are technical; useful subtitles/purposes remain. Rejected instructions have no booked movement.

Refunds/cash deposits are explicitly unsupported. Pending lifecycle changes, incoming bank transfers outside the observed buddy class, nonzero inline fees without a separate fee record, additional product/device variants and live no-account/empty-history responses remain source gaps. Unknown operation types, statuses, fees, currencies, graph relationships or malformed responses fail the whole synchronization. Historical live portal outages and its GET-only timeout retry remain in the archived pre-migration snapshot; no unobserved retry or short-lived portal-session fallback is part of the mobile-only implementation.

The official [iDenfy face browser documentation](https://documentation.idenfy.com/face-auth/FaceAuthenticationIframe) establishes the face-specific browser URL. Successful and rejected owner face attempts were observed before migration; the mobile registration/identity flow itself is unchanged. The prior 502 occurred after confirmed mobile identity on portal sessions/cloned, now removed. The first mobile-only Bootloader run on 2026-10-20 succeeded with 35 accounts and 8 transactions. Its bank requests used only api.zen.com: fast-login, v2/accounts and history-entries. Saved MobileAuth was present and no recovery override was enabled. The owner manually linked the accounts to existing accounts. The owner subsequently confirmed a repeated synchronization without another login or duplicates. This confirms the owner acceptance check for the existing mobile session and manually established account links; it does not establish automatic migration matching or month-long inactivity behavior.

The complete mobile-only cold connection was also verified on 2026-10-20: initial authentication returned 201, OTP/passcode verification, identity initialization, face attempt notification and final identity verification all returned 200. All 46 bank responses were successful and used only api.zen.com. The run loaded 35 accounts and 618 transactions over 36 history pages and saved complete MobileAuth before financial loading. This is observed cold-registration evidence, not a restored session.
