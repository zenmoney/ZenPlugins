## Граф счетов

Источник счетов — `getMyFinancesPage`, `accounts.accounts`. Связи с картами находятся в `limits[].cards[]`; значение `CLOSE` — наблюдавшийся признак закрытой карты. Отсутствие связей с картами или статуса карты считается ошибкой данных. Для счёта сохраняется банковский ID, номера без повторов передаются в `syncIds`, история загружается один раз на счёт. Признак архивности берётся из `closeDateS` или `archive`.

Этот отбор не определяет наличие кредита или овердрафта. Поле `limit` не является кредитным лимитом. `loanList`, `depositList` и `b2pCards` не считаются альтернативными представлениями счетов: в `b2pCards` находятся сохранённые карты получателей и платёжные карты. Для поддержки новых продуктов нужны подтверждённые связи между договором и счётом, а не догадки по названию.

Счёт с пустым исходным списком карт и без признака закрытия передаётся как `checking`; его тип подтверждён по банковскому договору. Скрытые в интернет-банке продукты не исключаются. Непустой список, состоящий только из закрытых карт, не означает счёт без карт. Закрытые продукты без карт не загружаются, пока их тип нельзя надёжно определить.

Карточные и текущие счета используют один метод API истории. Две исходные записи в `current-account-operation.json` покрывают исходящий перевод и входящее перемещение собственных средств, включая время без пометки часового пояса. Эти примеры не доказывают поддержку всех видов операций и истории любого счёта.

## Даты и пагинация

Момент операции берётся из `operDateTime`; `operDate` используется только при отсутствии времени. `state.dateS`, `sbpOperDateTime` и дата проводки из PDF его не заменяют. Формат без пометки часового пояса проверен на 16 парах API/PDF: время API соответствовало Москве, а выписка отображала тот же момент в UTC+7 с разницей в четыре часа. Это наблюдение относится к Левобережному и не считается общим правилом Фактуры. Неизвестный формат времени завершает синхронизацию с ошибкой.

`bankDay` рассчитывает календарные границы запроса. После загрузки операции отбираются включительно по исходным `fromDate` и `toDate`. Если `toDate` отсутствует, в запрос передаётся текущий день по Москве, потому что метод API требует конечную дату; дополнительная локальная верхняя граница по времени не добавляется.

История загружается через `pfmTape` с продуктом `AC_<accountId>` и `countForPage=50`. Веб-клиент банка передаёт в `lastOperationId` запись с индексом 48. Плагин сохраняет все записи и объединяет пересекающиеся страницы по банковскому ID. Неполная страница завершает пагинацию. Полная страница без новых ID и превышение предела в 1000 страниц считаются ошибкой.

## Авторизация и транспорт

Сначала проверяются сохранённые cookie-файлы, затем выполняется выданный банком SSO-переход. Успешный вход подтверждается через `loginInfo`, и только после этого авторизация сохраняется. Обновления cookie-файлов сохраняются после успешных запросов API независимо от результата последующей обработки счетов и операций.

Cookie-файлы хранятся вместе с путями и сроками действия и отправляются только на подходящие пути банка. Плоский заголовок остаётся только для совместимости со старыми сохранёнными данными. Если протухшая SSO-цепочка привела к форме входа, смешанное состояние мобильной сессии и Keycloak отбрасывается, после чего холодный вход начинается заново один раз.

При пустой настройке логина или пароля плагин может запросить значение во время ручной синхронизации. Поддерживается наблюдавшаяся OTP-форма из четырёх полей; код отправляется один раз. Повторная форма логина после отправки данных означает неверный логин или пароль. Повторная OTP-форма означает, что код отклонён или истёк. Другие формы остаются неизвестными ошибками: плагин не пытается угадать их смысл.

Фоновая авторизация разделяет пять состояний:

1. Если сохранённой банковской сессии нет, плагин завершает запуск с `UserInteractionError` до открытия SSO-формы.
2. Если сохранённая сессия ещё работает или восстанавливается через SSO без формы входа, синхронизация продолжается без логина, пароля и OTP.
3. Если банк отклонил сохранённую сессию и показал форму входа, плагин использует непустые логин и пароль из настроек подключения. Если банк принимает их без дополнительного подтверждения, обновлённая сессия сохраняется и фоновая синхронизация продолжается.
4. Если банк отклоняет логин или пароль и снова показывает форму входа, плагин завершает запуск с `InvalidLoginOrPasswordError` и не сохраняет неподтверждённую сессию.
5. Если данных входа нет или после их отправки банк показывает OTP-форму, плагин завершает запуск с `UserInteractionError`. В фоне он не вызывает `ZenMoney.readLine`, не отправляет OTP и не сохраняет промежуточную сесию.

Отправка логина и пароля — первый запрос, после которого банк может инициировать внешнее взаимодействие и прислать SMS. Узнать о необходимости OTP до этого запроса нельзя. Поэтому фоновая попытка продлить сессию может вызвать неиспользованное SMS, хотя сам код плагин не читает и не отправляет. Такое поведение требует согласования с сопровождающими, поскольку общий контракт ZenPlugins требует завершать фоновую авторизацию до запроса, который заведомо может потребовать участие пользователя.

Методика, хронология запусков и наблюдавшиеся границы `cookie`, `credentials` и `credentials + OTP` зафиксированы в разделе «Исследование авторизации» файла [STATUS](STATUS.md#исследование-авторизации). Таблица описывает ручные запуски Bootloader; плановая фоновая синхронизация им не подтверждена.

Запросы, переходы и действия форм ограничены HTTPS-доменом банка. Открытая часть цепочки сертификатов регистрируется через `ZenMoney.trustCertificates`, если этот метод доступен; системное или браузерное хранилище сертификатов не изменяется.

Полное журналирование HTTP отключено. В диагностике остаются пути методов API, коды ответа, сведения о сроках действия cookie-файлов и структура форм, но не значения cookie-файлов, скрытых полей и параметров перехода. Самостоятельный плагин не содержит доработок Bootloader для хранения копии данных входа.

## Ограничения преобразования

Остаток берётся из `availableWhenPay`; отсутствие значения или нечисловое значение считается ошибкой. Для поддерживаемых дебетовых счетов плагин всегда передаёт подтверждённый банковский остаток. Способ применения разницы задаётся отдельно для счёта в Zenmoney.

Валюта операции должна совпадать с валютой счёта. Явное значение `state.code` должно быть равно `successes`; отсутствие поля допускается для уже наблюдавшихся записей. Признак `hold` передаётся без изменений. Эти правила сами по себе не подтверждают поддержку всех вариантов блокировки, отмены и возврата.

Каждая исходная операция создаёт одно движение. Перевод между своими счетами объединяется после загрузки обеих историй, если реальные записи совпадают по известной паре счетов, валюте, абсолютной сумме и моменту операции. Исходящая сторона должна иметь `BETWEEN.MY.ACC` и `TRANSFER_OWN_INSIDE_BANK`, входящая — `OTHER.INCOME`. Оба банковских ID сохраняются в соответствующих движениях.

Общий банковский ID перевода не наблюдался. Поэтому два одновременных перевода одинаковой суммы между теми же счетами остаются неоднозначным случаем используемого ключа. Если второй счёт отключён или встречная запись отсутствует, имеющаяся сторона остаётся отдельным поступлением или расходом. Общие банковские комментарии удаляются только после объединения. Отдельная комиссия остаётся отдельной операцией; дополнительная комиссия не вычисляется.

Данные магазина разбираются из наблюдавшегося формата с разделителями `\\`: название, город и страна. MCC сохраняется при наличии. Полезные детали и назначение платежа попадают в комментарий без повторения названия магазина или получателя.

## Тестовые данные

Фикстуры содержат полные выбранные записи с заменёнными личными идентификаторами. В старых заменах номеров счетов не сохранялись префиксы продуктов, поэтому по ним нельзя определять тип продукта. Исходные журналы, выписки, сохранённая авторизация и локальная конфигурация не должны попадать в репозиторий.
